# Composable Adjudication ERC: Project Context

Technical context for anyone (human or agent) working in this repository. Keep this file strictly technical: no business development, outreach, or meeting logistics.

## Goal

Author a new ERC for **composable adjudication**: a single, minimal interface through which any on-chain contract can request and consume adjudications from any adjudication system (GenLayer, Kleros, UMA, or off-chain agent panels), with **escalation** (a first instance escalating on contest; the composer chooses which systems and in what order, up to off-chain ADR) and **composability** (an aggregate of adjudicators is itself an adjudicator). A second, adjacent ERC covers composition and use-case factories.

## Current phase

Drafting in natural language. **No code yet**; a reference implementation comes later. Deliverables live in this directory:

- `one-pager.md`: the pitch, escalation and composability.
- `erc-composable-adjudication-draft.md`: natural-language draft of ERC #1 (the core interface).
- `erc-adjudication-factories-outline.md`: idea outline for ERC #2 (composition + factories).
- `knowledgebase.md`: public background on the systems and platform facts informing the design (GenLayer, ZKSync-stack cross-chain, Kleros, UMA, EAS, EVM facts). Non-normative: implementation details of specific systems live there, **never in the ERC text**.
- `design-decisions-needed.md`: running to-do list of open design decisions, each with enough description to pick up cold. When decided: apply to the drafts, record in this file, delete from that one.

## Settled design decisions (binding; do not reopen without the user)

1. **New from zero + adapters.** The standard is designed from scratch. ERC-792/1497 are prior art only, never framed as something this standard breaks compatibility with. Existing systems (GenLayer, Kleros, UMA) integrate via adapter contracts implementing the new interface.
2. **Adjudication-native wording.** The unit of work is an *adjudication* (a case submitted for decision; a conflict is not required); the outcome is a *resolution*. Roles: *Adjudicator* (decides) and *Adjudicable* (consumes). Never use "dispute" or "ruling" except when referencing prior art.
3. **Core surface:** `registerAdjudication(definitionUID, data) payable → adjudicationId`; `activate(adjudicationId, evidenceUIDs, data) payable`; `status(adjudicationId)` ∈ `None / Registered / Active / Resolved`; `resolution(adjudicationId) → EAS attestation UID`; ERC-165 `supportsInterface` (required); events `AdjudicationRegistered`, `AdjudicationActivated`, `EvidenceLinked`, `Adjudicated`. Both `data` parameters are opaque implementation-defined call parameters (never semantic content; that lives behind EAS pointers). They exist because composites must relay child-specific parameters through a uniform signature and adapters need call-time parameters the definition doesn't carry. Parameter-capture rule (2026-07-30): `data` never chooses the forum. Outcome-steering process parameters (which system decides, court choice, juror count) SHOULD be fixed by the definition or deployment configuration, and Adjudicators SHOULD validate activation `data` against them; a deliberate departure from ERC-792's `extraData`, since under two-phase the activator is an adverse party and the first activator would otherwise capture the forum (evidence capture one layer up).
4. **Two-phase lifecycle: register, then activate.** Registration happens at agreement time (cheap/free, dormant; the on-chain arbitration clause); activation happens at contest time (unilateral, payable; where adjudication fees are due). Rationale: parties register while still cooperating, so one canonical `adjudicationId` exists from day one, which solves the competing-cases problem for agreements with no on-chain deal contract. The spec is silent on combining registration and activation in one transaction; a proposed MAY clause was removed as unneeded (2026-07-28), and decision 17 (no state skipping) already governs multi-transition transactions. Naming symmetry is deliberate: `register → Registered`, `activate → Active`, resolved → `Resolved`.
5. **Status is exactly four values.** `None` is required as the enum's zero value (unwritten storage slots read as zero, so zero must mean "does not exist"). No `Provisional` state and no `challenge()` entry point in ERC #1; both are explicitly deferred to future extensions.
6. **Composite pattern.** An escalation router or X-of-Y aggregator is itself an Adjudicator. "Rounds" are the ordered list of child adjudications. Composition semantics, including the `children()` introspection interface and the `AdjudicationDelegated` event, live in **ERC #2**, not in the core.
7. **ERC-165 required in core.** Every Adjudicator answers `supportsInterface` for the core interface ID. This is the discovery rail for all future extensions.
8. **Pull only.** The Adjudicator stores the resolution and emits `Adjudicated`; consumers read `resolution(adjudicationId)`. No callback into the Adjudicable.
9. **EAS everywhere semantic.** Adjudication definitions, evidence, and resolutions are EAS attestation pointers; schemas via an EAS registry. The ERC does not constrain the on-chain result type.
10. **Evidence is contest material, entering at activation; registration has no evidence parameter.** The baseline (the parties' agreement and context) lives in or behind the adjudication definition, committed while parties still cooperate. `activate` carries the activator's evidence UIDs; later submissions are implementation-defined. The normative evidence-to-case link is the on-chain `EvidenceLinked` event (EAS `refUID` to the definition is recommended for traceability but ambiguous alone, since one definition can serve many cases).
11. **Fees: channel standard, semantics out of scope.** `registerAdjudication` and `activate` are `payable` (registration SHOULD be cheap/free; activation typically carries the fees); amounts, currencies, refunds, who-pays are implementation-defined. Escalation funding is implementation-defined in v0.1; the funding patterns (pay-as-you-go vs pre-funded budget) are listed as future work in the ERC #2 outline. A `cost()` view is deferred to future extensions.
12. **The standard doesn't rank or order systems.** Never present escalation as "fast → secure" (which system is more secure is contestable; consider GenLayer's AI validators vs. bribable Kleros/UMA jurors) and never say the standard itself orders rungs by cost or anything else. The standard provides building blocks; the composer of a chain chooses the systems and their sequence. Cost differences (cheap AI resolution, costlier crypto-economic systems, off-chain ADR as the costliest) may be described as what typical compositions look like, not as a rule.
13. **v0.1 leaf implementations.** ERC #2 implements at least four leaf Adjudicators: a GenLayer adapter, a Kleros adapter, an **account adjudicator** (renamed from "wallet adjudicator" 2026-07-30: the mechanism is a `msg.sender` check against a fixed address, which authorizes an account, EOA or contract; a wallet is the off-chain key/software operating an account, and the resolver may be a Safe or ERC-4337 smart account, which is no wallet. The original rationale survives: name the leaf for the on-chain thing, never the operator, and "account" is the vocabulary of ERC-4337/6900/7579. Rejected: "EOA adjudicator" excludes contract accounts; "single-signer adjudicator" fails because contract accounts don't sign. Gloss at first mention: a single account, EOA or contract, authorized to resolve), and an echo adjudicator for testing (resolves on activation with a canned resolution read from its adjudication definition; an earlier "via `data`" branch was removed 2026-07-30 because the canned resolution is semantic content and the core bars semantics in `data`, and reference code doing it would license everyone to). An EAS designated-attester adjudicator (decision delivered as an attestation instead of a transaction) was considered and dropped from v0.1 (2026-07-28); the account adjudicator covers the trust model.
14. **Chain-agnostic.** Deploys on any EVM chain; cross-chain and off-chain mechanics are adapter concerns, invisible to the standard. System-specific architecture (how GenLayer, Kleros, or any other system is reached) belongs in `knowledgebase.md`, never in the ERC.
15. **Activation authorization is governed by the adjudication definition, enforceable because definitions are on-chain (see 16).** Precedence rule (fixed 2026-07-30; the old "registrant or parties" union wording accidentally granted third-party registrants activation rights): parties named in the definition → only they may activate (each unilaterally); definition explicitly opts into open activation → anyone; definition names no parties and no opt-in → registrant only. Registering never confers activation rights by itself. Parties SHOULD be able to link evidence after activation (defeats evidence-capture by a front-running activator). The activation-attack analysis lives in the draft's Security Considerations, rewritten 2026-07-30 to drop the false "bounded griefing" claim: the fee bounds only the attacker's cost (it pays the Adjudicator, not the victim, who bears capital lockup × duration), and against a fallible first rung a baseless contest on a large stake can be positive-EV. The draft now states activation as a unilateral right to impose adjudication duration, with value-at-stake sizing an explicit consumer-side decision. Never reintroduce boundedness claims.
16. **Attestation integrity is normative.** Definition and resolution attestation schemas MUST be registered irrevocable; resolution attestations MUST be on-chain; definition attestations MUST be on-chain **on the same chain as the Adjudicator** (changed 2026-07-30 from "MAY be off-chain": on-chain readability is what makes definition-governed rules like activation authorization enforceable rather than advisory; the zero-gas off-chain definition flow was given up for this). Definitions SHOULD be compact and content-addressed for bulky baseline material (content hashes, no mutable references). Definition and resolution attestations MUST have `expirationTime` zero (added 2026-07-30; rationale corrected 2026-07-31 after verifying EAS against its contracts: the original "revocation on a timer" reasoning was wrong, because EAS validates `expirationTime` only at attest time and ignores it thereafter, `getAttestation` returns an expired attestation unchanged, and `isAttestationValid` checks existence only. The real hazard is divergence rather than protocol invalidation: consumers that read the field treat the attestation as lapsed, those that do not treat it as live, and nothing on-chain settles which reading is correct. The mandate is unchanged and if anything better justified, since EAS itself will not enforce it). Two proposed bindings were considered and REJECTED (2026-07-30): resolutions referencing their definition via refUID, and resolutions attested by the resolving Adjudicator. Both are unnecessary because `resolution()` itself is the provenance (the UID arrives through the trusted contract's own storage), and a child returning a wrong-context UID is just a misbehaving child, which X-of-Y aggregation and escalation absorb by design. Rationale: `Resolved` finality is only real if the content behind the UID can be neither revoked nor withheld; otherwise consumers hold an immutable pointer to a repudiable statement. The pointer itself is equally frozen: once `Resolved`, `resolution()` MUST equal the `resolutionUID` emitted in `Adjudicated` and MUST NOT ever change (gap closed 2026-07-30; previously only status immutability was mandated, letting a hostile-but-conforming Adjudicator swap resolutions after consumers acted). Conformance-subject rewrite (2026-07-30): every integrity MUST now binds the Adjudicator as verifier (verify definition properties at registration and revert otherwise; verify resolution properties before entering `Resolved`), since attestation `revocable`, `expirationTime`, and existence are all readable on-chain from EAS. Schema-level phrasing ("schemas MUST be registered irrevocable") was dropped as subjectless and unobservable. Side effect: resolution attestations are now same-chain by necessity, because the Adjudicator can only verify on its own chain. The compactness guidance stays a SHOULD aimed at definition authors, explicitly binding no contract.
17. **No lifecycle state skipping.** Every adjudication passes through `Registered` and `Active` before `Resolved`; one transaction may perform several transitions, but each transition occurs and emits its event. Consequences in ERC #2: the no-adjudication passthrough activates-and-resolves on its uncontested path, and the echo adjudicator resolves on activation, never straight from registration.
18. **`adjudicationId`s are independent and registrant-bound, not "unpredictable."** Rewritten 2026-07-30: the earlier unpredictability MUST was untestable and contradicted by its own example (a hash over public inputs is predictable) and by the sign-then-register flow, which requires parties to precompute the id for their signed agreement. Normative properties: unique, never reused, dependent only on the registration's own inputs (no shared counters or other-registration influence, so sequential assignment is non-conforming), and revert on exact-tuple collision rather than reuse or overwrite. Deterministic derivation (hash over registrant, definitionUID, caller-supplied salt) is RECOMMENDED; squat resistance comes from registrant binding, not secrecy. The salt makes each input tuple unique, so duplicate definitionUIDs never fail. Precomputability is a feature, not a bug.
19. **No adoption-metrics framing anywhere in this repo.** The activation-rate/agreements-governed metric was a design aid, not for publication; it was removed from all documents (2026-07-28) and must not be reintroduced.
20. **`definitionUID` MAY be zero: Adjudicator-supplied definitions.** Zero means the Adjudicator itself supplies the definition (template Adjudicators with the definition fixed at deployment); implementations requiring a caller-supplied definition MUST revert on zero. `AdjudicationRegistered` MUST carry the definition UID actually governing the case (a template emits its fixed UID, never zero), keeping the event stream uniform for indexers. The `registerAdjudication(definitionUID, data)` parameter shape itself is settled as-is (2026-07-28).
21. **Liveness is named, not fixed.** Nothing in the standard forces an Adjudicator out of `Active` (no terminal failure state, no timeout, pull-only), so withheld outcomes (lost keys, extorting operators, stalled composite children, no exit even by mutual consent) are a real surface the standard cannot close. The draft's Security Considerations names resolution liveness as part of the trust in the chosen Adjudicator and adds SHOULD guidance: Adjudicables SHOULD NOT make irreversible commitments whose only exit is `Resolved`, and SHOULD have a fallback (deadline/default path, alternate route, mutual release). Liveness mechanisms inside adjudicators/composites are implementation concerns (2026-07-30).
22. **Atomic activate-and-resolve is discouraged for party-named cases.** For adjudications whose definition names parties, Adjudicators SHOULD NOT resolve in the transaction that activates; doing so gives the counterparty zero blocks to respond and voids the monitoring/evidence defenses. SHOULD NOT rather than MUST NOT: the echo adjudicator (test double) and the passthrough's uncontested path (no adverse party by construction; window elapsed before activation) remain conforming, and a MUST would require normative party detection before the schema encoding is settled. A minimum `Active` duration is a verifiable adjudicator property (same class as error rate and liveness); parties verify it before committing to an `adjudicationId`. Decision 17 (multi-transition transactions) is unchanged (2026-07-30).
23. **Review batch of clarifications (2026-07-30), all applied to the draft.** (a) `Registered` enum prose no longer claims "binding"; it reads "referenceable and permanent, but binding only on parties who committed to this `adjudicationId` out of band," resolving the contradiction with the orphan-registrations security text. (b) Template mirror case specified: a template Adjudicator MUST revert on a nonzero `definitionUID` unless it equals its fixed UID (prevents silent baseline substitution where the caller registers under X and the event says Y). (c) `status()` and `resolution()` MUST be `view` (staticcall-compatible). (d) RFC 2119 list expanded to include REQUIRED, SHOULD NOT, RECOMMENDED (all used in the text). (e) Adapter finality: an adapter MUST NOT report `Resolved` before the fronted system's outcome is final under that system's own rules; an irrevocable resolution overturned upstream cannot be corrected. (f) Resolution-timing discretion (operator chooses the publication moment, extractable for resolution-consuming markets) is accepted and documented as adjudicator trust. (g) Evidence UIDs carry no validity requirement; validation is explicitly implementation-defined and divergence is conforming.
24. **Escalation window source is a per-composite design choice (2026-07-30, closes open decision 5).** A composite MAY fix the window in its instantiation configuration or read it from the on-chain adjudication definition; both are enforceable now that definitions are mandatory on-chain, and which source a composite uses is part of its published design. The standard does not mandate one source. A config-only mandate was proposed (case/process split, schema coupling, per-instance auditability) and declined by the user: implementations get both options. The earlier objection that definition-sourced windows are unenforceable rested on the removed off-chain-definitions premise and no longer applies.
25. **X-of-Y panel aggregation directions (2026-07-30, details at implementation time).** Adopted at idea level: window-based exclusion of unresolved children (the pool shrinks, the threshold X never lowers, so stalling a child can never reduce the quorum) and a no-quorum outcome declared in the definition's outcome space when X becomes unreachable (panel failure is a legitimate resolution; the core keeps no failure state). Handling of non-conforming child resolutions (wrong schema, outcome outside the definition's space) is implementation-defined. Operator independence of the Y children is implementation-defined, not standardized (sybil operators are indistinguishable on-chain by construction). The last-mover problem (public child resolutions make the final unresolved child the casting vote and the bribery target; commit-reveal impossible while resolutions are on-chain verified attestations) is recorded in the outline's Future Work as a known open issue; a commit-reveal or encrypted-resolution adjudicator variant may address it later.

## Design decisions needed (open; do not resolve unilaterally)

- **EAS schema field lists (core ERC): highest priority.** Definitions are on-chain and Adjudicators decode them to enforce activation authorization (decision 15), so the definition schema's layout must be normative or enforcement fragments per implementation and definitions stop being portable between Adjudicators. Candidate field lists for all three schemas are drafted in `design-decisions-needed.md` §1. Two sub-points are settled by verification against the EAS contracts (2026-07-31, facts recorded in `knowledgebase.md`): the canonical schema UID **can** be a chain-independent constant (preimage is `keccak256(schemaString, resolver, revocable)` with no chain id, so identical strings match across chains, provided `resolver = address(0)`); and **layout-prefix compatibility is REJECTED**, because partial `abi.decode` over attestation data whose leading field is a dynamic `address[]` silently misdecodes instead of reverting on a short payload, and attacker-controlled ABI offsets let a prefix decode disagree with a full decode about who may activate. Consequence: one canonical schema decoded whole, gated on `attestation.schema == constant`; extension goes through the opaque `bytes processParams` field, never a varied schema. Only schemas a contract reads need normative layout: definition (read by the Adjudicator) and resolution (read by composites); evidence does not.

- **ERC-20 fee channel.** `payable` channels only the native asset, but real systems price fees in tokens (e.g., UMA's USDC bonds), and token-denominated fees are stable across the registration→activation gap where ETH-fixed fees drift. An adapter fronting a token-priced system has no standard way to receive the fee: approve-then-pull is an unblessed convention every adapter will vary; `data` is barred from semantic content; ETH→token swaps inside a fee payment add slippage/MEV. Bites hardest in composites: an escalation router funding an ETH-fee child and a USDC-fee child breaks generic composition at the funding layer. Candidate resolutions for co-authors: bless approve-and-pull normatively (adapter announces its fee token) vs. keep native-only with pre-funded token balances in adapters. Recorded in `design-decisions-needed.md`. **Cost-shifting sub-point appended 2026-07-31 for circulation** (`design-decisions-needed.md` §4): standardizing loser-pays is not proposed, since the shapes diverge too far across Kleros and UMA for decision 11 to survive it. The open question is whether **`cost()` should leave "future extensions" and be decided together with this item**: composites cannot fund children without it, and a bare `uint256` is already wrong once fees can be token-denominated. Interface IDs cannot freeze until both land.

## Things to look at (parked; raised in review, deliberately not acted on yet)

- **Post-activation evidence entry point.** The security model leans on parties responding after activation, but the core defines no standard `linkEvidence`-style function and the response right is SHOULD-level. Left to implementations for now; revisit whether the core (or an extension) needs a normative entry point or a mandatory response window.
- **Escalation economics (ERC #2).** The "later rungs discipline earlier ones" claim classically depends on loser-pays bonds, while fee semantics are out of scope. Also unaddressed: a downstream adjudicator spiking fees during the escalation window to price out escalation, and who is authorized to call `escalate`. Handle when ERC #2 is drafted.
- **EAS as a normative dependency.** EIP editors may reject a normative reference to a deployed product rather than a standard; a possible rephrase keeps the architecture but defines parameters as opaque `bytes32` commitments with EAS as the RECOMMENDED binding. Revisit at submission time.
- **`resolution()` before `Resolved`: "revert or return zero".** Two observably different conforming behaviors; consider mandating return-zero (composes better in multicalls) when signatures freeze.

## Conventions

- **No em dashes, anywhere, in any file of this repo.** Restructure the sentence instead: colons, semicolons, commas, parentheses, or separate sentences. This includes the ERC drafts, internal docs, commit messages, and all future writing. (Arrows `→` in state diagrams and mappings are fine; they are not em dashes.)
- **Write in the register of the best-written ERCs.** Short declarative sentences. RFC-2119 keywords carry the normativity; the prose around them stays plain. Definition lists use colons. No rhetorical flourish, no suspense, no asides; state the rule, then its reason.
- **The ERC text is always clean and self-contained.** No open questions, to-dos, process notes, or references to repo files or co-author workflow inside the ERC drafts; prior-art links are inlined. Anything undecided or ongoing goes to `design-decisions-needed.md`.
- **The documents carry no narrative of their own evolution.** The ERC drafts and the design docs state what is; how the text got there lives only in this file, the dated decision log. Drop narrative past about the documents themselves ("was considered and rejected", "is now ruled out") and state the position and its reason in the present. The test is subject, not tense: a dated marker on an open item in `design-decisions-needed.md` ("Mostly settled (2026-07-30)") reports current status and stays; prose about how a sentence came to read as it does goes.
- **Lifecycle verbs are exact.** Adjudications are *registered* and *activated*, never "created" or "opened." A composite *registers* a child (that is when `AdjudicationDelegated` fires) and usually activates it in the same transaction. Contract instantiation uses *deployed*, keeping deployment vocabulary distinct from the case lifecycle.
- Adjudication systems are enumerated in **alphabetical order** (GenLayer, Kleros, UMA); no system gets first billing anywhere in this repo. Chainlink is not referenced (removed 2026-07-28).
- Specs are natural language, not Solidity; terminal-only workflow for now.
- Record every new design decision in this file as it is made.
